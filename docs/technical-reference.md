## 2. Domain model

Fourteen tables: `trips`, `trip_items`, `trip_notes`, `resources`, `settings` (migration 001);
`expenses`, `payments` (migration 002, N5, see §13); `travellers`, `trip_travellers`,
`item_participants`, `lists`, `list_items`, `templates`, `template_uses` (migration 003, Fieldbook
Part C, see §14).

### Two independent axes on a TripItem

| Axis | Values | Purpose |
|---|---|---|
| `kind` | `transport` `stay` `activity` `food` `task` `other` | **Structural.** Drives behaviour and which form fields appear |
| `status` | `idea` `confirmed` `cancelled` | **Commitment.** Drives which tab it appears in |

`subkind` is a third, **non-structural** field for icons, labels and filtering. It replaces the
transport-mode concept entirely — there is no separate `TransportMode`.

**It is a fixed enum per kind, not free text** (decided M2): free text fragments into
cafe / café / Coffee and cannot drive icons reliably. Defined in `src/domain/tripItem.ts`:

| kind | subkinds |
|---|---|
| `transport` | flight · train · bus · ferry · car · taxi · transfer · walk |
| `stay` | hotel · apartment · hostel · guesthouse · camping |
| `activity` | museum · gallery · tour · attraction · event · theatre · outdoor · spa |
| `food` | restaurant · cafe · bar · bakery · market |
| `task` | check-in · booking · document · packing |
| `other` | luggage · insurance · parking · shopping · viewpoint |

### `details` is pinned to transport

Only `transport` has a structured `details` shape — `from`, `to`, `carrier`, `number`, `seat` —
because a journey has two endpoints and `location_name` holds one. Every other kind is served by
title, location and notes, so their `details` stays permissive rather than guessing at fields.

`detailsSchemaFor(kind)` drives validation; `transportDetails(item)` and `routeLabel` read it back
as 'Sofia → Bergamo'. Unknown kinds stay permissive so a backup from a later version still parses.

### Editing must not pin an inherited zone

`TripItem` carries both the resolved `start`/`end` moments and the raw `startTzOverride` /
`endTzOverride`. The resolved moment is for reading; the override is what an edit writes back.
Feeding the resolved zone into the form would silently pin an item that was meant to follow the
trip, so `tripItemFormValues` uses the override.

**`subkind` is always nullable, and no list contains `'other'`** — "unspecified" is expressed by
the absence of a subkind, never by a magic value. Adding a subkind is a code change, not a
migration, since the column has no CHECK constraint.

### Tabs are queries, not entities

```sql
-- Places: unrated sits BELOW maybe, not among it
WHERE trip_id = ? AND status = 'idea'
ORDER BY CASE priority
           WHEN 'must' THEN 0 WHEN 'want' THEN 1 WHEN 'maybe' THEN 2 ELSE 3 END, title

-- Bookings: no tab uses this since the design handoff (decision log D20); kept and tested.
-- (The Expenses tab's *Bookings* view is booking COSTS, derived from items in TypeScript — §13.)
WHERE trip_id = ? AND status = 'confirmed'
ORDER BY (start_utc IS NULL), start_utc, title

-- Search: title, notes, location_name, address, confirmation_code
WHERE trip_id = ? AND (title LIKE ? ESCAPE '\\' OR ...)

-- Timeline and Next are NOT queries — see below
WHERE trip_id = ? AND status != 'cancelled'
ORDER BY start_utc
```

### Timeline and Now are derived in TypeScript

Timeline and the Now card are the exception to "tabs are queries". `src/domain/timeline.ts` takes
a trip's items and derives both. SQL only loads and orders the rows.

A multi-day item produces **two** timeline entries — start and end — so a hotel check-out or an
overnight train's arrival lands on the day it actually happens. A single row becoming two ordered
entries is not something the query should try to express, and a trip holds tens of items, not
thousands, so deriving in memory costs nothing.

**Now is `nowSections`** (`src/domain/itinerary.ts`, D27): *Happening now* (confirmed, timed, not a
task or a stay, at most 24 hours long; from its start until 15 minutes after its end, or 60 minutes
after a start with no end), *Today, no fixed time* and *Maybe today* (date-only, confirmed or idea,
today in the item's own zone), then *Up next* with nothing above repeated. `useNow` also refreshes
when the app returns to the foreground.

One consequence: **the Now card considers check-out entries too**, not just `start_utc`. At 08:00
on your last morning, "Check out 11:00" is genuinely the next thing you have to do, and the
`start_utc >= now` query alone would never surface it.

| Rule | Where |
|---|---|
| Group by local day, order by instant | `buildTimeline` |
| Multi-day splits into two entries | `timelineEntries` |
| Date-only sorts above a real `00:00` | `compareEntries` |
| Cancelled excluded; tasks on Now only under Open tasks | `timelineEntries` / `nowSections` |
| Not scoped to the trip's dates — a flight the day before counts | `nowSections` |

### Search escapes the user's wildcards

`%` and `_` are LIKE wildcards, so searching for `50%` would otherwise match the whole trip.
`searchPattern` escapes them and every statement declares `ESCAPE '\\'`. A blank query returns
null and the caller skips the query entirely, so an empty box shows nothing rather than everything.

Search covers `trip_notes` too — a door code you typed into a note should be findable from the
same box. **Cancelled items stay searchable on purpose:** finding the cancellation confirmation is
the reason the row was kept.

Known limit: SQLite's `LIKE` is case-insensitive for ASCII only, so `Café` will not match `cafe`.
Acceptable for a personal trip; fixing it would mean a normalised search column.

### Status semantics

| Status | Appears in | Notes |
|---|---|---|
| `idea` | Places, and Timeline if dated | May carry `priority`. A dated idea is a plan that is not booked — render it visually distinct |
| `confirmed` | Bookings, and Timeline if dated | |
| `cancelled` | Item lists only, greyed | **Excluded from Timeline and Now.** The row is kept deliberately: a cancellation confirmation PDF is attached to it |

`completed_at` applies to `kind='task'` only. For a booking, "completed" is derivable
(`end_utc < now`); for a task it is not, because it depends on the user acting.

## 3. Schema

```sql
PRAGMA journal_mode = WAL;   -- once at creation; persisted in the file
PRAGMA foreign_keys = ON;    -- EVERY connection; NOT persisted

CREATE TABLE trips (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  destination TEXT,
  start_date  TEXT NOT NULL,        -- 'YYYY-MM-DD' date-only. MANDATORY
  end_date    TEXT NOT NULL,        -- 'YYYY-MM-DD' date-only. MANDATORY
  default_tz  TEXT NOT NULL,        -- IANA, e.g. 'Europe/Rome'
  cover_path  TEXT,                 -- RELATIVE path under documents dir
  notes       TEXT,

  traveller_count INTEGER,
  travellers      TEXT,             -- JSON array of names, optional

  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE trip_items (
  id       TEXT PRIMARY KEY,
  trip_id  TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,

  kind     TEXT NOT NULL
             CHECK (kind IN ('transport','stay','activity','food','task','other')),
  subkind  TEXT,
  status   TEXT NOT NULL DEFAULT 'idea'
             CHECK (status IN ('idea','confirmed','cancelled')),
  priority TEXT CHECK (priority IN ('must','want','maybe')),

  title    TEXT NOT NULL,

  -- See §4. Four columns per timestamp, by design.
  start_local     TEXT,   -- 'YYYY-MM-DD' | 'YYYY-MM-DDTHH:mm' — no offset, no Z
  start_tz        TEXT,   -- IANA; NULL falls back to trips.default_tz
  start_precision TEXT CHECK (start_precision IN ('date','time')),
  start_utc       TEXT,   -- DERIVED sort key. Repository layer writes this, nothing else

  end_local       TEXT,
  end_tz          TEXT,
  end_precision   TEXT CHECK (end_precision IN ('date','time')),
  end_utc         TEXT,

  completed_at TEXT,      -- kind='task' only

  location_name TEXT,
  address       TEXT,
  latitude      REAL,
  longitude     REAL,

  confirmation_code TEXT, -- on the item, NOT a resource
  notes             TEXT,
  details           TEXT, -- JSON, Zod-validated, discriminated by `kind`

  price_amount   INTEGER, -- MINOR UNITS (4250 = 42.50). Never REAL
  price_currency TEXT,    -- ISO 4217
  is_paid        INTEGER NOT NULL DEFAULT 0,

  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

  CHECK (start_local IS NULL OR start_precision IS NOT NULL),
  CHECK (end_utc IS NULL OR start_utc IS NULL OR end_utc >= start_utc),
  CHECK (price_amount IS NULL OR price_currency IS NOT NULL)
);
-- DELIBERATELY no constraint tying item dates to the trip's date range:
-- flight check-in and "book restaurant" are dated before the trip starts.

CREATE INDEX idx_items_trip_start  ON trip_items(trip_id, start_utc);
CREATE INDEX idx_items_trip_kind   ON trip_items(trip_id, kind);
CREATE INDEX idx_items_trip_status ON trip_items(trip_id, status);

CREATE TABLE trip_notes (
  id         TEXT PRIMARY KEY,
  trip_id    TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  title      TEXT NOT NULL,
  body       TEXT NOT NULL DEFAULT '',
  pinned     INTEGER NOT NULL DEFAULT 0,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_notes_trip ON trip_notes(trip_id, pinned DESC, sort_order);

CREATE TABLE resources (
  id           TEXT PRIMARY KEY,
  trip_id      TEXT REFERENCES trips(id)      ON DELETE CASCADE,
  trip_item_id TEXT REFERENCES trip_items(id) ON DELETE CASCADE,

  kind    TEXT NOT NULL CHECK (kind IN ('file','link')),
  subtype TEXT NOT NULL DEFAULT 'generic'
            CHECK (subtype IN ('generic','ticket','confirmation','wallet','maps','website')),
  label   TEXT NOT NULL,

  url         TEXT,     -- kind='link'
  stored_path TEXT,     -- kind='file'. RELATIVE to documents dir. NEVER absolute
  file_name   TEXT,     -- original filename, for display
  mime_type   TEXT,
  size_bytes  INTEGER,

  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,

  CHECK ((trip_id IS NULL) <> (trip_item_id IS NULL)),   -- exactly one owner
  CHECK ((kind = 'link' AND url IS NOT NULL)
      OR (kind = 'file' AND stored_path IS NOT NULL))
);

CREATE INDEX idx_resources_item ON resources(trip_item_id, sort_order);
CREATE INDEX idx_resources_trip ON resources(trip_id, sort_order);

CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- 'default_travellers'        JSON array — powers "usually travel with"
-- 'default_currency'          ISO 4217
-- 'notification_lead_minutes' integer as text
```

**Migration 002 (`src/db/migrations/002-expenses.ts`, N5)** — purely additive: two tables and one
nullable column. No existing row is rewritten. It carries N5b's splitting columns (`paid_by`,
`split`, `payments`) unused, so the phone needs this one migration for the whole of N5
(decision log D25).

```sql
CREATE TABLE expenses (
  id       TEXT PRIMARY KEY,
  trip_id  TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  category TEXT NOT NULL CHECK (category IN ('food','groceries','transport','activities',
                                             'shopping','accommodation','other')),
  label    TEXT,                     -- optional; the UI titles a label-less expense by category
  amount   INTEGER NOT NULL CHECK (amount > 0),   -- MINOR UNITS
  currency TEXT NOT NULL,            -- ISO 4217; never converted
  spent_on TEXT NOT NULL,            -- 'YYYY-MM-DD', a local date
  notes    TEXT,
  paid_by  TEXT,                     -- N5b, unused in N5a
  split    TEXT,                     -- N5b JSON, unused in N5a
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idx_expenses_trip ON expenses(trip_id, spent_on);

CREATE TABLE payments (              -- N5b "settle up"; unused in N5a
  id TEXT PRIMARY KEY,
  trip_id   TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  from_name TEXT NOT NULL,
  to_name   TEXT NOT NULL,
  amount    INTEGER NOT NULL CHECK (amount > 0),
  currency  TEXT NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_payments_trip ON payments(trip_id);

-- A receipt is a resource with trip_id = the expense's trip AND expense_id set, so the
-- one-owner CHECK on resources still holds and the table is not rebuilt.
ALTER TABLE resources ADD COLUMN expense_id TEXT REFERENCES expenses(id) ON DELETE CASCADE;
CREATE INDEX idx_resources_expense ON resources(expense_id);
```

**Migration 003 (`src/db/migrations/003-fieldbook.ts`, Fieldbook C1–C5)** — purely additive: seven
new tables and their indexes; no existing table is altered and no existing row is read or written.
The SQL is in the file, commented; the design is `docs/fieldbook-plan.md` §4.1. Three choices to know:

- `trip_travellers.traveller_id` and `item_participants.traveller_id` are `ON DELETE RESTRICT`: a
  profile in use cannot be deleted, and the screen says where it is used (FB-11).
- `lists.trip_id` NULL is a reusable list; a trip copy names its source in `source_list_id`, and
  `template_uses.template_id` names its template — **provenance, not foreign keys** (FB-19), so a
  per-trip backup can leave the source out and deleting a template leaves its trips alone.
- `templates.content` is one Zod-validated JSON document (`domain/templates.ts`), applied whole and
  never queried (FB-16).

`migrate` also sets `PRAGMA busy_timeout = 5000` on every open, and switches to WAL only when the
file is not already in WAL: a reopen after a font-scale change could meet the previous connection
still closing and fail with *database is locked* (FB-20).

**Receipts and the trip-document queries.** Because a receipt has a `trip_id`, every query that
reads resources by trip must decide about it: `SELECT_RESOURCES_FOR_TRIP` (Trip documents)
excludes `expense_id IS NOT NULL`; `SELECT_ITEM_RESOURCES_FOR_TRIP` joins through items, so never
sees one; `COUNT_TRIP_CONTENTS` counts them (deleting a trip takes its receipts);
`SELECT_ALL_STORED_PATHS` includes them (the sweep keeps their files). `INSERT_RECEIPT` takes the
trip id from the expense row, so a receipt can never name a trip other than its expense's.
`ResourceOwner` has a third scope, `expense`.

### Conventions

- **Ids** are UUIDs from `expo-crypto`, generated in app code. No autoincrement.
- **Timestamps** are TEXT ISO strings. No integer epochs, no SQLite date functions.
- **Money** is INTEGER minor units. Binary floating point cannot represent `0.10` exactly and the
  error compounds on any sum. Format to `€42.50` at the UI edge only.
- **Booleans** are INTEGER 0/1.
- **No `sort_order` on `trip_items`** — ordering is temporal, or priority+title for undated items.

### Change notifications

`SQLiteProvider` **must** be opened with `options={{ enableChangeListener: true }}`:

```tsx
<SQLiteProvider databaseName={DATABASE_NAME} onInit={migrate}
                options={{ enableChangeListener: true }} useSuspense>
```

It defaults to `false`. Without it `addDatabaseChangeListener` never fires, so `useLiveQuery`
never refreshes and screens show stale data — with **no error and no warning**. Verified on device
in M2, where a newly created trip did not appear on Home.

Events arrive **one per row changed**. `useLiveQuery` does not answer each: a read starts after
50 ms without a new event on its tables (at most 10 s after the first), and while a read runs at
most one more is queued (0.10.0). Every change is still followed by a read that starts after it.
Before, a batch write re-read and re-rendered every mounted query per row, between the batch's own
statements — 300 imported activities took 43 s, minutes with Timeline and Places open; now ~3 s.
`useReminders` already waited for 600 ms of quiet.

### What a read's state means on screen (R4)

`useLiveQuery` returns `{ data, error, loading, refetch }`. A failed read keeps the data it had and
retries after 300 ms, 1 s and 3 s; after that the error stands until a watched table changes or
`refetch` is called. Its state is valid **only for the inputs it was read for**: when `deps`
change (another trip, another item) it reads as loading from that very render, never showing the
previous record as this one's.

Screens read it through `queryView` (`src/hooks/queryView.ts`, tested): `loading`, `failed`
(first read failed), `missing` (read worked, record gone — the **only** state that may say *no
longer exists*), `empty` (a list with nothing in it — the only one that may say *nothing here*),
`ready`; and `isStale` (a refresh failed, earlier data shown). `src/ui/components/QueryStates.tsx`
draws them: `QueryScreen` for a screen's main record, `LoadFailed` in place of a list,
`StaleNotice` above a screen's content. Edit forms are filled once from their record, so they use
the gate only, not the stale notice. Search keeps the last results while the next search runs.

### Migrations

Hand-written, append-only, numbered: `src/db/migrations/001-initial.ts`, `002-….ts`.
`PRAGMA user_version` holds the applied version. Run via `SQLiteProvider`'s `onInit`.

**Never edit a shipped migration** — add a new one. There is no ORM and no schema-diffing tool.

**A migration and its `user_version` commit together.** `migrationBatch(migration)` appends
`PRAGMA user_version = N` to the migration's SQL and `migrate` runs the batch in one transaction.
Before 0.3.0 the version was written in a separate statement afterwards, so an app killed in
between had the tables but not the version, re-ran the migration and failed on `CREATE TABLE`.
The migration tests run the same batch the app runs.

`migrate` uses `withExclusiveTransactionAsync`. That is fine here, unlike for imports (§12): it runs
in `onInit`, before any screen subscribes to changes.

Migrations are tested from a database shaped like the phone's (`002-expenses.test.ts`: one of
everything, awkward values, rows compared before/after, a failing batch leaves nothing). Before
0.3.0 shipped, 002 was also run on a copy of the owner's real rows; all came through identical.

| # | Release | What it adds |
|---|---|---|
| 001 | 0.1.0 | `trips`, `trip_items`, `trip_notes`, `resources`, `settings` |
| 002 | 0.3.0 | `expenses`, `payments`, `resources.expense_id` (N5) |

## 4. Time and timezones

### The failure being prevented

Store a flight departure as a UTC instant. Depart Sofia 06:10 (UTC+3 in September), land in
Bergamo, the phone switches to UTC+2 — the app now displays **05:10**. Every zone crossing makes
the itinerary lie. The same bug moves a date-only hotel check-in to the wrong day.

### The rule

**Store what the ticket says, plus where it says it. Derive everything else.**

| Column | Example | Role |
|---|---|---|
| `start_local` | `2026-09-19T06:10` | Wall clock. No offset, no `Z`. **Immutable truth** |
| `start_tz` | `Europe/Sofia` | IANA zone. NULL → `trips.default_tz` |
| `start_precision` | `time` \| `date` | Stored, not inferred |
| `start_utc` | `2026-09-19T03:10:00Z` | **Derived** sort/filter key |

- `start_local` renders as `06:10` in Sofia, in Milan and at home. It is never recomputed.
- `start_utc` exists so ordering and "what's next" happen in SQL rather than by loading every row
  into JS. It is a **cache**, written only by the repository layer.
- `start_precision` is stored because **`T00:00` is a real time** and must stay distinguishable
  from "date known, time unknown". That is user intent, not a formatting detail.

### Derived rules

```
Day grouping:   substr(start_local, 1, 10)     -- local date. NEVER group by start_utc
Within a day:   ORDER BY start_utc
Countdown:      start_utc - Date.now()
Date-only item: start_utc = local midnight -> naturally sorts to the top of its day
Trip is past:   end_date < today's device-local date
```

Grouping by UTC would push a 23:30 Sofia event onto the previous day. Grouping by local date
never does.

"Trip is past" uses the **device-local** date deliberately: while travelling the device zone *is*
the trip zone, and a 01:00 landing back home correctly flips the trip to past.

### Precision is read off the text, never passed in

`tripItemInputSchema` takes a moment as `{ local, tz? }` and derives `precision` from the shape of
`local` via `localPrecision`. A caller cannot submit `'2026-09-19'` labelled `time`, because the
inconsistent pair has nowhere to live. `'2026-09-19T00:00'` is still `time` — a real midnight.

### A NULL zone follows the trip, and instants are rebuilt when it moves

`start_tz`/`end_tz` are stored NULL when the user did not override the trip's zone, so the item
keeps meaning "whatever this trip is in". That matters because the zone is autofilled from the
device and is easy to get wrong at creation: fixing it on the trip fixes every item at once,
rather than leaving twenty items in the zone you happened to be standing in.

The cost is that the cached instants derived from the old default go stale, so `updateTrip` calls
`recomputeTripInstants` whenever `default_tz` actually changes. It rewrites `*_utc` only for rows
with a NULL `*_tz`; a row stating its own zone is untouched. The wall-clock text never changes.

### A journey's zone, read off its city (N6, 0.3.1)

A NULL zone follows the trip, which is right for most items and wrong for a journey end in a city on
another clock: a departure from Munich on a Helsinki trip, entered as 08:15 with no zone, sorted
and counted down as 08:15 Helsinki — an hour early — while the screen still showed 08:15. Found in
the owner's real data. `src/domain/zoneHints.ts`, pure and tested:

| Function | Rule |
|---|---|
| `zoneForPlace` | Exact, case-insensitive, trimmed match of the zone search's places (`TIMEZONE_PLACES`) plus each zone's own city. A place listed under several zones maps to null |
| `differentClock` | Resolve the same wall-clock time in both zones; different instants = different clocks. On the day, so summer time counts |
| `zoneSuggestion` / `withSuggestedZone` / `withLegZones` | Fill a time's zone from its end's city when the time has none, has a time of day, and the city's clock differs from the trip's |
| `zoneHint` | Explain a zone that equals the city's and differs from the trip's: the line under the time |
| `zoneMismatches` | Times saved without a zone whose city keeps another clock: the detail-page notice. A time stating its own zone is never flagged |
| `withMomentZone` | The item with one end's zone set, validated by `tripItemInputSchema`, so a change putting the end before the start is refused |

Only `transport` items (From/To in `details`) and journey legs. Undo (*Use Helsinki time*) **pins**
the trip's zone rather than clearing it, or the city would refill it; *Use the trip's timezone* in
the picker does the same only when the city would refill, and clears otherwise. The form fill is
one pure step per change — `withLegZones` in `JourneyFields`, one effect in `ItemForm` — because a
fill per field would let two ends filled in the same render overwrite each other.

### Known limitation

If the IANA database changes an offset (a country abolishing DST), cached `*_utc` values go stale.
Negligible for trips booked months ahead. `recomputeTripInstants` already does the rewrite; it
would just need calling on a different trigger.

### Library — RESOLVED (M1 spike, on device)

**`date-fns` v4 + `@date-fns/tz` works on Hermes with no polyfills.** Verified on Android 16 /
RN 0.86 / Hermes, not just in Node. Do **not** add `@formatjs/*` — it is hundreds of KB and is
not needed.

Confirmed on device:

| Check | Result |
|---|---|
| Sofia 06:10 → UTC (+3) | `2026-09-19T03:10:00.000Z` ✅ |
| Rome 14:00 → UTC (+2) | `2026-09-19T12:00:00.000Z` ✅ |
| London spring-forward boundary | `2026-03-29T02:30:00.000Z` ✅ |
| date-only → local midnight | `2026-09-18T22:00:00.000Z` ✅ |
| 23:30 event keeps its local day | `2026-09-19` ✅ |
| countdown | `92` minutes ✅ |

Also verified in Node across device zones from UTC+14 to UTC−10 — identical results, which is the
whole point of the design.

**`Intl.supportedValuesOf('timeZone')` is ABSENT on Hermes.** The timezone picker therefore uses a
curated list in `src/domain/timezones.ts`. A test asserts every id in it actually resolves — it
caught two invalid ids on first run (`Europe/Reykjavik` → `Atlantic/Reykjavik`, `Asia/Doha` →
`Asia/Qatar`), which would otherwise have produced `NaN` instants silently.

An invalid IANA id makes `TZDate` return `NaN` rather than falling back to a default zone, so bad
input fails loudly. Keep it that way.

`Temporal` is Stage 4 but not in Hermes. The polyfill is 20KB+. Not for MVP.

## 5. Files and offline storage

### Import rule

**Copy on import, always. Never persist an external URI.**

```ts
const picked = new File(externalUri);              // content:// on Android
const dest   = new File(Paths.document, `media/${id}.pdf`);
await picked.copy(dest);                           // ASYNC — see below
// store 'media/<id>.pdf' in resources.stored_path
```

**`copy()` returns a promise in 57.0.6 and must be awaited.** Unawaited, the row can be written
before the file lands, and a crash in between leaves a ticket that opens to nothing. There is a
`copySync()` if a synchronous path is ever needed; `delete()` and `exists` are already synchronous.

The stored name comes from the resource id, not the original filename, so two files both called
`ticket.pdf` cannot collide. The extension is taken from the reported mime type first and the
filename only as a fallback — Android frequently reports a PDF under a meaningless name.

Reasons:
- Android grants only **temporary** URI permission. Reading a stored `content://` URI a week later
  abroad fails.
- Share-intent payloads land in a cache path the OS can reclaim.
- The original file may be deleted or moved by the user.

### Attaching: three pickers, and receipts before their expense exists

`src/features/resources/attach.ts` has one picker per source — `file` (expo-document-picker,
several at once), `photo` (image library, several), `camera` (asks the CAMERA permission and
throws `CameraPermissionError`, which the screen turns into *Open Settings*) — and two ways to use
them:

- `attach(db, owner, kind)` picks, copies each file in and writes its row at once, one file at a
  time so one unreadable file does not cost the others. Items, trip documents and an existing
  expense's receipts use it.
- `importAsInput` copies **one** file in without a row. The share sheet uses it (R5, D27):
  `saveShare` copies each shared file, collecting the names of those that fail, then writes the
  new item (if any) and every row in **one** transaction (`saveSharedRows`,
  `src/repositories/share.ts`). If that write fails, the copies are deleted at once; if no file
  copied, nothing is written. `shareOutcomeMessage` (`domain/share.ts`) is the alert for a partial
  share: what was saved, what was not, and which item to share into again.
- `pickAndImport(kind)` copies files in **without a row**, for a new expense whose id does not
  exist yet. The form holds the `ResourceInput`s and `createExpense` writes them with the expense
  in one transaction.

A copy no row will ever point at is deleted at once: removing a pending receipt, or leaving the
new-expense form unsaved, calls `deleteStoredFile` (media paths only, best effort). The form does
not delete once a save has started, since rows may already point at the files; a save that throws
has rolled back and re-enables the cleanup. Anything a kill leaves behind is the start-up sweep's.

A label comes from the file name (`defaultFileLabel`), except names that mean nothing — a
media-store id (`37.png`) or a generated UUID (the camera's) — which get the picker's fallback,
*Document* or *Photo*.

The documents' buttons are *File · Photo · Link*; a receipt's are *Camera · Photo · File*.

### Paths are relative

`resources.stored_path` holds `media/<uuid>.<ext>`, joined to `Paths.document` at read time.
The app sandbox path is **not stable across reinstalls**; an absolute URI in the database means
every ticket silently fails after a reinstall.

`Paths.document` is the correct directory — it is not system-reclaimable. `Paths.cache` is.

### Cleanup: GC, not inline deletion

SQLite cascades rows, not files. **On app start**, list the media directory and delete any file
not referenced by a `resources.stored_path`. Crash-safe, self-healing, and correct regardless of
how an orphan arose. `useMediaSweep` runs it once per launch from inside the provider.

**The sweep's one dangerous property:** an empty reference list means "delete everything", which
is correct for a fresh install and catastrophic after a failed read. So the query result is never
defaulted — if loading the paths throws, the sweep does not run at all. The decision itself
(`orphanedStoredPaths`) is pure and unit tested; only the deletion touches the disk.

`toStoredPath` returns null for anything outside the documents directory or outside `media/`, so
a path that does not round-trip can never be handed to `delete()`.

### Links are restricted to schemes we will open

`http`, `https`, `geo`, `mailto`, `tel`. A `file:`, `content:`, `intent:` or `javascript:` URL is
refused at the schema, since a link can arrive from the Android share sheet (M8) and be opened
later with a tap.

Before deleting a Trip or TripItem, show a confirmation **naming the blast radius**:
*"Delete Milan? This removes 6 items and 11 saved files."* These may be the only copies.

### Opening a stored file — RESOLVED (M1 spike, expo-file-system 57.0.6)

**Use `file.contentUri`. Do not import `getContentUriAsync`.**

```ts
import { File } from 'expo-file-system';
import * as IntentLauncher from 'expo-intent-launcher';

const file = new File(Paths.document, storedPath);
await IntentLauncher.startActivityAsync('android.intent.action.VIEW', {
  data: file.contentUri,   // synchronous property, Android-only
  flags: 1,                // FLAG_GRANT_READ_URI_PERMISSION
  type: file.type,         // mime type, also a property
});
```

What the spike established by reading the installed package's declarations:

1. `getContentUriAsync` is **not** part of the modern `File`/`Directory`/`Paths` API.
2. It *is* re-exported from the package root — but as a **throwing** deprecation shim
   (`build/legacyWarnings.d.ts`, which calls `errorOnLegacyMethodUse` and throws). So
   `import { getContentUriAsync } from 'expo-file-system'` **compiles fine and fails at runtime.**
   This is a trap: TypeScript will not catch it.
3. The real implementation still exists at `expo-file-system/legacy`, but is unnecessary.
4. `contentUri` is a **direct property on the `File` class** (`NativeFileSystemFile`), documented
   as "A content URI to the file that can be shared to external applications. @platform android".

So the modern API covers the whole file layer with no legacy import anywhere:

| Need | Modern API |
|---|---|
| path | `file.uri` |
| existence | `file.exists` |
| size | `file.size` |
| mime type | `file.type` |
| copy in | `await sourceFile.copy(destFile)` (or `copySync`) |
| delete | `file.delete()` |
| create dir | `new Directory(Paths.document, 'media').create({ intermediates: true })` |
| list (for GC) | `directory.list()` |
| share to other apps | `file.contentUri` |

**`File.pickFileAsync()` is not a replacement for `expo-document-picker` — verified on device in
S2.** It picks and copies fine, but on Android its `name` is the SAF document id (`document:35`),
so every attachment was labelled with it. `DocumentPicker.getDocumentAsync` returns the real
display name. It is called with `copyToCacheDirectory: false`: copying straight from the
`content://` URI into `media/` works, and skips a second copy through the reclaimable cache.

Opening via `file.contentUri` was verified on the emulator (Android 17) with **airplane mode on**:
the Drive PDF viewer renders the stored copy. Its title bar shows the stored name
(`<uuid>.pdf`), a cosmetic cost of naming files by id.

### Missing-file handling

`file.exists` is a boolean property. A resource whose file is gone must render as unavailable with
a clear message, not crash and not silently show nothing.

## 7. Native / Expo boundaries

**No custom native code is required.** One third-party config plugin is.

| Need | Mechanism |
|---|---|
| SQLite, files, picker, linking, notifications, localization, intent launcher | Plain Expo APIs |
| Android package name, notification icon/colour, `POST_NOTIFICATIONS` | `app.json` config |
| Android share sheet | **`expo-share-intent` v8+** (config plugin) |
| Anything else | *nothing* — no Kotlin, no ejecting |

### Share-to-App

`expo-share-intent` **v8.0+** is the SDK 57 line (v7 → SDK 56, v6 → SDK 55, v5 → SDK 54).

1. **Requires a custom dev client.** Expo Go cannot run it.
2. **Cold start works** — it is deep-link based, so sharing to a closed app launches it with the
   payload.
3. **Default `androidIntentFilters` is `["text/*"]`** — URLs and text only. Use
   `["text/*", "application/pdf", "image/*"]`. **Not `"*/*"`**, which puts the app in the share
   sheet for everything.
4. **Copy the incoming file immediately** (see §5). Temporary URI permission plus a reclaimable
   cache path.
5. **Validate the payload with Zod.** This is untrusted input from other applications.
6. **Risk:** the only non-Expo native dependency. It will gate future SDK upgrades.

**How it actually works on Android (checked against v8.0.1's source in S7).** Deep links are only
the iOS path. On Android the share starts `MainActivity`, which is `singleTask`, with `ACTION_SEND`.
The native module copies each shared file into the app's `cacheDir` and hands JS a `file://` path,
so point 4 is already met by the time JS runs. The app then imports that path into `media/` on
save. `ShareIntentProvider` wraps the root layout, and `ShareLanding` pushes `/share` whenever a
share is present, both at cold start and while running. The screen reads the payload once and
clears it. `disableIOS: true` keeps prebuild from generating an iOS extension for an Android-only
app.

### Notifications

Local/scheduled notifications work on Android in SDK 57. Push is not used at all.

`POST_NOTIFICATIONS` on Android 13+ needs an **explicit runtime permission request** at a sensible
moment in-app — a manifest entry alone is not enough.

A notification may reference a deleted item. Resolve the id at tap time and fail gracefully.

**Built in S6.** Open question 4 was answered by the owner:

| Kind | Reminds |
|---|---|
| Travel | 3 hours before departure |
| Stay | 09:00 on the check-in day (or at check-in, if that is earlier) |
| Activity, food, other | 1 hour before |
| To do | at its own time |
| Anything with a date but no time | 09:00 on that day |

Times are worked out in the **item's own zone**, so a Sofia departure reminds at 03:10 Sofia time
wherever the phone is. Only confirmed, dated, unfinished items remind. Each item has an on/off
switch, stored as `details.reminder = 'off'`. It is off only when set, so existing rows needed no
migration. The rules are pure and tested in `src/domain/reminders.ts`.

**Reconcile, don't track writes.** `src/notifications/reminders.ts` compares the reminders the
database calls for with what is scheduled, cancels the difference and schedules the rest (the
notification id is the item id). `useReminders` runs this at launch and after any change to
`trip_items` or `trips`, debounced. So create, edit, cancel, restore, delete, import and a trip zone
change are all handled in one place, with no reminder code at those call sites. Syncs are queued
one at a time, because two overlapping syncs would each schedule the other's reminders again. At
most 64 reminders are scheduled, nearest first, well under Android's per-app alarm limit.

**Permission** is asked right after saving an item that would remind (new, edit, move to timeline),
never at launch. After a refusal Android won't prompt again, and the app stays quiet.

**Exact alarms.** Without them, Android delivers a reminder within a window that grows with how far
ahead it was scheduled. The emulator showed about 2 minutes on a 3-minute reminder, so a
week-ahead flight reminder could arrive very late. The app declares `USE_EXACT_ALARM`, which is
granted at install on Android 13+ and makes `expo-notifications` use `setExactAndAllowWhileIdle`.
Google Play restricts that permission to alarm and calendar apps, which doesn't matter for a
sideloaded personal app. Revisit it only if the app ever goes to the Play Store.

**Patched to survive memory pressure** (found in phone QA). When an alarm fires, expo-notifications
relays through two more broadcasts (trigger → receive → present), and the app is idle between them.
On the phone, a minute after a restart, Android's low-memory killer ended it in that gap and the
reminder was never shown. `patches/expo-notifications+57.0.20.patch` presents it inside the alarm's
own receiver whenever the app isn't in the foreground. In the foreground the relay is kept, so the
JS handler still decides. Expo ships this module as a prebuilt AAR, so `package.json` lists it in
`expo.autolinking.android.buildFromSource`. Without that entry the patch is silently ignored:
check the build log for `:expo-notifications:compileReleaseKotlin`.

A tapped reminder opens its item through `useLastNotificationResponse`, both from a running app and
from a cold start. The response is then cleared, so returning to the app later doesn't reopen it.

### Google Wallet

Store the Wallet link as a `resource` with `subtype='wallet'` and open it. Nothing more.

**Gate and terminal are deliberately not stored.** Wallet auto-updates because the *airline pushes*
changes into Google's pass API — it is the airline doing it, not Wallet reading anything. Without
an airline feed that is not reproducible, and scraping airline sites is fragile and ToS-hostile.

So: Wallet is the live pass, this app is the index. Store the Wallet link *and* a link to the
airline's manage-booking page. `seat` may live in `details` — it is assigned at booking and stable,
unlike the gate.

### Maps

`expo-linking` to a `geo:` URL (*Open in Maps*, U5) or a Google Maps directions URL (§15). No
embedded map; a full-day map is roadmap Phase 5.

## 12. Export and import

The only guard against data loss, so the format is deliberately dull: raw rows, not domain
objects. A restore reproduces the database exactly and is unaffected by any later refactor of the
domain layer.

```
travel-organizer-backup-2026-09-11.zip
  backup.json          formatVersion, app, exportedAt, tables{...}, files[]
  media/<id>.<ext>     every file any resource points at
```

**Format 2** (0.3.0, `EXPORT_FORMAT_VERSION`) added `expenses`, `payments` and
`resources.expense_id`. A **format-1** backup (0.2.0) still imports: the Zod schema defaults the
missing tables to `[]` and `expense_id` to null. A newer format is refused. `EXPORT_COLUMNS` lists
every table's columns, and a test fails if a table in the schema is missing from it — it caught
exactly that while N5 was built. On import, expenses are written before resources, so a receipt's
`expense_id` always has its row.

**Format 3** (0.6.0) added the seven tables of migration 003, each defaulting to `[]`, so formats
1 and 2 still import. Rows owned by a trip (`trip_travellers`, `item_participants`, a trip's lists
and their items, `template_uses`) follow their trip exactly as items do. App-level rows
(`travellers`, reusable lists and their items, `templates`) behave like settings: *merge* inserts
only ids not already here, *replace* also updates rows with the same id (`upsertSharedRow`) —
an upsert, never a delete, so RESTRICT cannot bite. The insert order keeps every foreign key valid
at each step: travellers → trips → trip_travellers → items → participants → notes → expenses →
payments → resources → lists → list_items → templates → template_uses (the ordered `TABLES` map
in `repositories/backup.ts`). A per-trip export (`filterTablesForTrip`) carries the travellers the
trip uses.

**Formats 4 and 5** (0.7.1) add `classification` on `travellers` / `trip_travellers` and
`trips.converted_travellers`; the Zod schema defaults them (`'unspecified'`, `'[]'`), so formats
1–4 still import.

**Format 6** (0.8.0) adds `listItemRecipients`. A format-1–5 document is passed through
`upgradeDocument` on parse: each list item's `traveller_id` becomes its one recipient, exactly
as migration 006 does on the phone. On import, recipients are written only for list items the
import itself writes (`insertLinkRow`, `INSERT OR IGNORE`), so *Keep mine* never adds people to an
item already here. `EXPORT_FORMAT_VERSION` is **6**.

**Export reads one snapshot (A4).** `readTables` runs inside `withExclusiveTransactionAsync`, whose
second connection holds one WAL read snapshot for every table, so a write landing mid-export can
not produce a backup with an item but not its trip. It only reads, so the change-listener caveat
below does not apply. The archive is built in memory (`fflate`), so its size is bounded by the
phone's memory.

**Files are read in chunks (QA of 0.6.0).** `File.bytes()` returns the whole file as one array on
the app's Java heap (growth limit 192 MB on the test emulator): a 100 MB attachment made every
export fail with OutOfMemoryError, and a 150 MB backup could be made but not restored. Since
0.6.0 `readFileBytes` (`files/storage.ts`) reads 4 MB at a time (`readInChunks`, domain, tested)
into one buffer outside that heap. A picked backup is copied into the cache by the picker first:
a handle on the provider's `content://` URI lost its descriptor part-way through (*Bad file
descriptor*). Measured on the emulator (4 GB RAM): a 380 MB backup exported; a backup with one
150 MB file exported and restored.

`backup.json` carries every table verbatim plus a **file manifest** — one entry per distinct
file listing every resource that references it, since two resources can share one file.

### Open question 5, resolved: one archive for everything

The purpose is protection against data loss, and a per-trip archive makes that a chore you have to
remember for each trip — a forgotten trip is lost data, which defeats the point. So the backup is
**one archive containing everything**.

It does not foreclose the other option. `filterTablesForTrip` produces the same structure for a
single trip, so exporting one trip later needs no format change and no second importer — it is the
same document with fewer rows. A test asserts the scoped document still parses.

### Importing

| Mode | Trips | Settings |
|---|---|---|
| `merge` | A trip already present is left alone, and its children are dropped from the write so nothing orphans. Importing the same backup twice is a no-op | `ON CONFLICT DO NOTHING` — a key already on this device keeps its value; a key it has never had is brought across |
| `replace` | The trip is deleted first and the cascade clears its children, then the backup is written | `ON CONFLICT DO UPDATE` — the backup wins |

**Settings follow the same rule as trips, decided by the SQL rather than by the plan.** They were
originally always overwritten, which made `merge` silently replace the "usually travel with"
default — the one place merge did not mean merge. `MERGE_SETTING` / `REPLACE_SETTING`.

**`replace` deletes before inserting rather than using `INSERT OR REPLACE`.** `REPLACE` deletes
the conflicting row to make room, and with `ON DELETE CASCADE` that would take the children out
*after* they had been written. Deleting the trip first makes the order explicit.

The whole import runs in one transaction, so a bad row aborts everything rather than leaving a
half-restored database. It is `withTransactionAsync` on the main connection, **not**
`withExclusiveTransactionAsync`: the exclusive form opens a second connection whose writes the
change listener never reports, so every open screen would keep showing the pre-import data. A backup from a **newer** `formatVersion` is refused outright instead of
being partly read, and manifest paths are validated with the same `isStoredPath` guard as the
media directory, so a tampered archive cannot write outside it.

The confirmation names what will be added (`summariseImportPlan`): *Adds 1 trip, 24 items, 2 notes,
2 expenses and 18 saved files. 1 trip already here is left as it is.* The expenses clause appears
only when there are some, so a format-1 backup reads as it always did. Receipts count as saved
files.

`planImport` reports `missingFiles` — rows whose file is not in the archive — so the UI can say
what will not open rather than restoring a dead reference silently.

### Two things S1 and S5 should know

`tripItemInputSchema(defaultTz)` returns a **new schema object on every call**, so a form must
`useMemo` it or react-hook-form rebuilds its resolver on every render.

A `trip_items` id colliding across two trips aborts an entire import rather than skipping the row.
With UUIDs this cannot realistically happen, but the failure is all-or-nothing by design — a
half-restored database is worse than a refused one.

### The archive (built in S5)

`src/domain/archive.ts` builds and reads the zip in memory with `fflate`, so it is tested in node:

- `packBackup` writes `backup.json` (deflated) and every stored file under `media/` (stored as is —
  PDFs and photos are already compressed). It refuses to pack a path outside `media/`.
- `unpackBackup` returns a reason instead of throwing when the file is not a zip, has no
  `backup.json`, holds damaged JSON, or comes from a newer format. **Only `media/<file>` entries
  are kept**, so a crafted archive cannot write anywhere else.

`src/files/backupFiles.ts` moves the bytes. Export reads every table and stored file, writes the
zip to `Paths.cache` and hands it to the share sheet with `expo-sharing`. Import picks any file
(providers label zips inconsistently, and unpacking explains a wrong one), shows the plan's summary
for confirmation, then **writes files before rows**: if the rows fail, the new files are orphans the
start-up sweep collects, never rows pointing at nothing. A stored file already on the phone is kept,
since stored names are unique ids.

`File.bytes()` is asynchronous (`bytesSync()` exists); `File.write()` takes a `Uint8Array`.

## 14. Lists, travellers, prices per person, the itinerary PDF, templates (Fieldbook C)

The design and every decision behind it: `docs/fieldbook-plan.md` §4 and §5 (FB-1…). Schema:
migration 003 (§3), plus 004/005 for adult/child (§15). Backup: format 3 (§12). What follows is where things live.

### Travellers (C2)

A profile is a name only (`domain/traveller.ts`, `repositories/travellers.ts`). A trip picks its
people (`trip_travellers`, ordered); an item picks a subset (`item_participants`). None picked on
an item means *not specified*, never "everyone". Links are by id, so a rename reads everywhere.
`deleteTraveller` is refused while the profile is used, and `travellerUses` says where (RESTRICT
is the backstop, the check is the message). The old free-text `trips.travellers` stays as it was;
`legacyNames` lists the names a trip still holds that are not profiles, and each becomes one only
by a tap (FB-12) — nothing is merged across trips. `createTripItem` / `updateTripItem` write an item
and its participants in one `withTransactionAsync`; `insertTripItem` is the part for callers that
already hold a transaction (`share.ts`).

### A price per person (C3)

Stored in the item's `details` JSON, not a column: `details.pricing = { mode: 'perPerson', lines:
[{ label?, quantity, unitAmount }] }` in minor units (`domain/pricing.ts`). `price_amount` keeps the
computed total, because every cost calculation already reads it. The item schema refuses a
`pricing` whose total does not match `price_amount` (`pricingMatches`), a zero quantity, or a total
past `Number.MAX_SAFE_INTEGER` (`pricingTotal` returns null). On a journey the pricing goes on the
first leg only, like its price (`journey.ts`). `pricingText` shows the working.

### Lists (C1)

One `lists` table for reusable lists (`trip_id` NULL) and trip copies (FB-15); ticks (`done_at`)
exist only on trip copies. `copyListToTrip` makes new rows with no ticks and names its source;
`countTripCopies` is what warns before copying the same list twice. `addToPacking` turns a bought
shopping item into an unticked packing item — buying is not packing, and nothing in a list ever
becomes an expense. `PRESET_LISTS` are offered when there are no reusable lists. Progress
(`listProgress`) counts rows, not quantities.

### Templates (C5)

`templates.content` is one `templateContentSchema` document of tasks, notes and lists. A task keeps
`offsetDays` from the trip's first day plus an optional `HH:mm`; `taskStart` rebases it onto the
new trip, read in the new trip's zone. `applyTemplate` writes everything in one transaction with new
ids and records a `template_uses` row, which warns before the same template is applied twice.
Bookings, prices and documents are never in a template.

### The itinerary PDF (C4)

`domain/itineraryHtml.ts` builds the whole document as an HTML string, pure and tested: a summary
of stays and travel, every trip day (empty ones say so) plus days before and after, both ends of a
journey in their own zones named by city, documents named and never linked. Every string typed by
the owner goes through `escapeHtml`. `DEFAULT_PDF_OPTIONS` keeps names, references, tasks, lists and
costs out until switched on (FB-18). Page numbers come from CSS `@page` margin boxes, which
Android's WebView prints.

`files/itineraryPdf.ts` prints it with `expo-print` (A4, 595 × 842 pt), copies the result to
`cache/itinerary/<Trip>-itinerary-<date>-<time>.pdf`, deletes the printer's temporary file, and
opens the share sheet. The cache is right for it: the PDF is a snapshot that can be made again.

## 17. Single-trip archive (2B, 0.9.0)

Rationale: D34. Plan and audit: `docs/phase2-plan.md`. Code: `domain/tripArchive.ts` (pure, all
rules), `repositories/tripImport.ts` (the transaction), `files/tripArchiveFiles.ts` (bytes, hashing,
staging), screens `app/trip/[tripId]/export-trip.tsx` and `app/import-trip.tsx`.

### Format

```
<Trip>-trip-YYYY-MM-DD-HHMM.zip
  manifest.json   { kind: "travel-organizer-trip", formatVersion: 1, rowFormat: 6, schemaVersion: 6,
                    app {name, version}, exportId, exportedAt, sourceTripId,
                    trip {name, destination, startDate, endDate},
                    attachments: "included" | "excluded", partial,
                    data {name: "trip.json", sizeBytes, sha256},
                    files [{name, status: included|excluded|missing, sizeBytes, sha256, mimeType}] }
  trip.json       { kind, tables: trips(1), tripItems, tripNotes, resources, expenses, payments,
                    travellers (only those the trip uses), tripTravellers, itemParticipants,
                    lists (trip copies), listItems, listItemRecipients, templateUses }
  files/NNN.ext   each distinct file once; resource rows point at these names
```

**Versioning rules.** `formatVersion` versions the layout; `rowFormat` is the backup's
`EXPORT_FORMAT_VERSION` the rows follow; `schemaVersion` is the exporting database's
`user_version`. An archive with any of them newer than this app reads is refused (*made by a newer
version — update the app first*), never partly imported. A future change to row shapes bumps
`rowFormat` with the backup format; a change to the layout or manifest bumps `formatVersion`. Never
in an archive: settings (so not Me), templates, reusable lists, other trips, other travellers.

### Limits (`TRIP_ARCHIVE_LIMITS`)

Archive 500 MB (checked before reading); 2,000 entries; 200 MB per file and 20 MB per JSON document;
600 MB unpacked in total — all from the zip's directory, before inflating. The archive is read and
built in memory, as the full backup is; a 120 MB attachment imported on the 4 GB emulator.

### Import

`openTripArchive` (untrusted input): size → directory pass (`unzipSync` with a `filter` that only
records; refuses `backup.json`, repeated names, any name but `manifest.json`, `trip.json` and
`files/<plain name>`, unknown compression, oversize entries) → inflate → manifest (`kind`, versions,
Zod) → data size + SHA-256 → rows (the backup's Zod schemas) → `checkTripArchive` (one trip, ids
unique, every owner and reference inside the archive, no duplicate pairs) → files (any present must
be listed `included`; each `included` checked for size and SHA-256 — a mismatch or absence is
`damaged`, and the screen asks before importing without it).

`planTripImport`: new UUID for the trip and every row; foreign keys through one map per table;
travellers new unless chosen `existing` (two archive travellers linked to one profile collapse to one
membership/participant/recipient); a new stored path per distinct file
(`media/<first row's new id>.<ext>`), shared again by every row that shared it; a file that did not
arrive leaves its row pointing at a path that does not exist (*Missing — attach again*);
`details.journeyId` remapped per journey; `lists.source_list_id` and `listItems.traveller_id`
cleared; `templateUses` kept with the new trip id. `uniqueTripName` adds *(2)*, *(3)*.

`importTripArchive`: write each file (target must not exist), read it back, check size + SHA-256 →
`applyTripImport` (one `withTransactionAsync`: travellers → trip → … → template uses,
`rebuildAllTripInstants` — caches only, `updated_at` kept — and the `trip_imports` record) → on any
failure: rollback + delete the files written → after commit `verifyTripImport` (row counts per
table) and file existence; a shortfall is reported, not undone.

**Crash window:** between the first file write and the commit, a kill leaves new unreferenced files;
the launch sweep (`useMediaSweep`) deletes them. Rows are written last, so no row can point at a file
that was not written. Verified on the emulator (E2E I4/I5).

**Duplicates:** `earlierImport(manifest, settings.trip_imports, trip ids)` → same export, another
export of the same trip, or the original on this phone (only imports whose trip still exists count).
The record lives in `settings` (no migration), so a full backup carries it.

**Known limitations:** archives are built and read in memory (the limits above bound it); exported
zips stay in the app cache until Android reclaims it; when the disk is full the message shows
SQLite's secondary "cannot rollback" error rather than "storage full".

## 18. Activities format: AI import and selective export (2C, 0.10.0)

Rationale: D35. Plan: `docs/phase2c-plan.md`. **Public description:** `docs/ai-activities-format.md`
and `docs/schema/travel-organizer-activities-v1.schema.json`. Code: `domain/activityFormat.ts`
(limits, parser, mapping, export), `activityFormat.schema.json` (the JSON Schema the app shares — a
test keeps the docs copy identical), `activityTemplate.ts` (AI instructions + example),
`activityDuplicates.ts`, `activityImport.ts` (preview model, selection, notices), `currencies.ts`
(ISO 4217 list), `repositories/activityImport.ts` (the write; item links for export),
`files/activityFiles.ts` (pick, read, share), screens `app/trip/[tripId]/import-activities.tsx` and
`export-activities.tsx`.

### Format (version 1)

`{ format: "travel-organizer-activities", version: 1, activities: [...] }` — 1–300 activities, ≤ 1 MB
UTF-8, nesting ≤ 6. Activity fields and limits: the public doc. Nothing in it names a table, a
column or an id.

### Mapping to the model

| Format | `TripItemInput` / row |
|---|---|
| `kind` (activity · food · stay · transport · other, default activity) | `kind`; `task` is refused |
| `type` | `subkind` when valid for the kind; otherwise dropped with a warning |
| `status` idea · planned (default idea) | `idea` · `confirmed`; anything else makes the activity invalid |
| `priority` | `priority` on ideas; dropped with a warning on planned |
| `date` + `startTime` | `start.local` `YYYY-MM-DD[THH:mm]` |
| `endDate` / `endTime` | `end.local`; omitted when it would say nothing (same day, no time) |
| `timeZone` / `endTimeZone` | `start.tz` / `end.tz` (IANA names only); the end takes `timeZone` when it has none; absent = follows the trip (`NULL`) |
| `location.{name,address,latitude,longitude}` | `location_name`, `address`, `latitude`, `longitude` (both or neither) |
| `description`, `notes` | `notes` = description, blank line, notes |
| `price.{amount,currency}` | `price_amount` (minor units: strings by `parseAmount`, numbers only with ≤ 2 decimals), `price_currency` (`^[A-Z]{3}$`; outside ISO 4217 = warning) |
| `links[]` | `resources` rows `kind='link'`, http(s) only; subtype `guessLinkSubtype`, label `defaultLinkLabel` when absent |
| `transport.{from,to,carrier,number}` | `details` (transport only) |
| — | `is_paid = 0`, no confirmation code, no participants, no `completed_at`, no reminder choice; ids made by the app |

Every activity goes through the same `tripItemInputSchema(trip.defaultTz)` the forms use.

### Validation tiers (`parseActivityFile`)

1. **Fatal file** — size; empty; not JSON (after removing a BOM and one surrounding Markdown fence);
   a `__proto__` / `constructor` / `prototype` key anywhere; depth > 6; wrong `format`; `version`
   not a positive integer, or newer than 1; `activities` missing, not a list, empty or > 300.
2. **Invalid activity** — every problem collected (wrong types, limits, calendar dates, times, zones,
   coordinates, amounts, currency shape, status, kind, links, end before start).
3. **Warnings** — type not of its kind, priority on a plan, outside the trip's dates, planned without
   a date, unknown currency, a zone with nothing to apply to.
4. **Ignored fields** — every key the format does not have, at any level, reported with a reason
   (per-person prices, ids, references, paid, people, files, timestamps, reminders, seats); the value
   is never read.

### Duplicates (`findActivityDuplicates`)

Normalised titles (NFD, no accents, lower case, punctuation → space). A candidate matches an item in
the trip (any status) or an earlier valid entry in the file when (1) the titles are equal, the times
compatible (same day and, if both timed, same time — or either undated) and the places do not
contradict (both located and > 1 km apart, or differently named); or (2) a timed start equals the
other's and the places are the same (name, or ≤ 100 m). Likely duplicates start unticked; the reason
names the other item and its date.

### Write

`importActivities(db, tripId, entries)`: one `withTransactionAsync` (checks the trip exists, then
`insertTripItem` + `createResource` per link). Any failure rolls back the batch. Add-only.
Reminders follow from the reconciler for planned, dated, future items — the preview counts them with
the same `reminderFor`. After the write the screen lists the new ids live (*Review imported
activities*); there is no bulk delete.

### Export (`buildActivityExport`)

Offered: ideas and plans of every kind but `task`; never cancelled items. Written: only the format's
fields; `startTzOverride` → `timeZone`; an end whose zone differs from the start's → `endTimeZone` (a
NULL end zone written as the trip's zone, so it means the same in another trip); links only of
subtype `website` / `maps` with http(s) URLs ≤ 2048. Each activity is re-read with `parseActivity`;
one that would not import again is excluded and named, never altered. File:
`<Trip>-activities-YYYY-MM-DD.json` in the cache, shared as `application/json`.

### Versioning

`format` is permanent. Version 1 never gains a field or a meaning; anything new is version 2 with its
own schema file. The app reads every version it ever read and refuses a newer one whole.

**Known limitations:** the preview renders every row (no virtualisation) — at 300 rows one toggle
costs ~200 ms on the software-rendered emulator; an exported file stays in the cache until Android
reclaims it; per-person prices wait for Phase 3.

## 19. Plan with AI: the planning context (2D, 0.11.0)

Rationale: D36. Plan: `docs/phase2d-plan.md`. Code: `domain/planningContext.ts` (allowlist, scrub,
intentions, builder — pure), `repositories/planningContext.ts` (`readPlanningInput`, selects only),
`SELECT_TRIP_TRAVELLER_CLASSIFICATIONS` in `db/queries.ts`, screen `app/trip/[tripId]/plan-with-ai.tsx`.
No writes, no network, no migration.

### Allowlist

`planningItemOf(item)` is the only code that reads a stored item. It returns `null` for tasks and
cancelled items, and otherwise exactly: `kind`, `subkind` (when valid), `status` (idea or
confirmed), `priority` (ideas), `title`, `start`/`end`, `startTzOverride`/`endTzOverride`,
`locationName`, and for transport `from`/`to`; `id` is kept only to break ties in ordering and is
never written. `planningInputOf` also collects the trip's `confirmation_code`s — used only to scrub
them. `readPlanningInput` reads the trip row, its items and `trip_travellers.classification`
(no names selected); notes, resources, expenses, payments, lists, templates and settings are not read.

| In the text | When |
|---|---|
| Destination (else trip name), dates, default zone | always |
| Planned items (not stays): day, time(s), zone where it differs, role (*Departs*/*Arrives*…), title, kind/type, place name or route | always |
| Planned without a date; before / after the trip | always, own sections |
| Ideas: title, kind/type, place, priority, *considering <date>* | switch, on |
| Stays: nights covered + place name (else title) + kind of stay | switch, off — **never** in the daily itinerary, never an address |
| Traveller counts: total, adults, children, not specified | switch, off — numbers only |
| Request: preset text or own words (≤ 500, verbatim) | always |
| Instructions + compact activities-format block | always |

Never: notes, descriptions, addresses, coordinates, links, booking references, carrier, flight
number, seat, journey id, reminders, prices, paid state, receipts, documents, expenses, payments,
lists, names, Me, ids, other trips, to-dos, cancelled items.

### Scrub (`scrubPlanningText`, titles / place names / route / destination)

Best effort, stated on screen. Removes (→ `…`): URLs (`http(s)://`, `www.`), emails, the trip's
booking references as whole words (case-insensitive, ≥ 3 characters, regex-escaped), runs of digits
with phone/card separators holding 9+ digits unless they contain a real calendar date, digit runs of
10+. Keeps dates (`2026-11-21`, `21.11.2026`), times, road and route numbers, flight numbers and
ordinary names. Whitespace collapsed.

### Rules

Days are `tripDates(trip)`; entries from `buildTimeline` over planned non-stay items (so overnight
items split, ordered by instant). An empty day says *Nothing planned yet*; 3+ consecutive empty
days collapse to one range. Times are the stored wall clock; a zone is named (`zoneName`, *Sofia
time*) when that end's zone differs from the trip's; a full entry with both ends shows `a–b` (same
zone) or `a → b`. Deterministic: no timestamp; ideas by priority, title, id; stays by start, title,
id; ties by id. Output ends with a newline.

### Screen

Presets / own words, three switches, the *never included* line, the warning *Review this text before
sharing. Activity titles and place names may contain personal information.*, the exact text
(selectable) and its length, pinned **Copy for ChatGPT** (`expo-clipboard`) and **Share**
(`react-native` `Share.share({ message })`) — both receive the one memoised string that is
rendered. Choices are not saved.

**Known limitations:** the scrub cannot recognise every kind of personal data in free text; the

## 20. Who is going: new items and joining a trip (3B, 0.12.0)

Rationale: D37. Plan: `docs/phase3-plan.md` §16. Code: `domain/participation.ts`

| Path | Participants written |
|---|---|
| Item form, new plan or saved place (any kind) | every current trip member, ticked by default, in `trip_travellers.sort_order`; editable before saving |
| Item form, new to-do | none |

| Leaving a trip | that trip's participation of that person deleted (unchanged) |

**Candidates** (`SELECT_JOIN_CANDIDATES` + `joinCandidates`): items of the trip that are not
`kind = 'task'`, not `status = 'cancelled'`, and that the person is not on. Plans
(`status = 'confirmed'`): upcoming — not yet ended, by `toInstant(end ?? start)`, a date-only moment
lasting to the next midnight in its zone — soonest first; then undated by title; then past, most
recent first. Saved places (`status = 'idea'`) by title. Ties: title, then id.

**Write** (`addTravellerToItems`): refuses (throws, writes nothing) when the person is not a member
of the trip; then per distinct id `INSERT … SELECT … WHERE` the item is in that trip, not a to-do,
not cancelled, `ON CONFLICT DO NOTHING`. Returns the rows added. Touches no `trip_items` column
(`updated_at` included), no other person's participation, no setting.

**Screens.** The new-item screen waits for the trip's travellers before opening the form (so the
default is never empty by accident; a failed read shows the usual retry). The Travellers screen
opens the sheet after each way of joining when there is something to offer, and from a member's
sheet (*Add to existing plans…*) at any time; with nothing to offer that action says so. In *Your
travellers*, a profile whose name another profile shares has the subtitle `namesakeHint`:
*Adult · On Lapland, Rome +1*.
